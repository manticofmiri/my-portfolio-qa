💡 TIL

xfail is not the same as ignoring a test

When I first used @pytest.mark.xfail, I thought it was just a way to skip tests that don't pass yet. I was wrong.

xfail means I expect this to fail, and here's why — it's a way to document a known bug without hiding it. If the test suddenly passes, Pytest marks it as XPASS and alerts you. That's actually useful: it means the bug got fixed, intentionally or not.

@pytest.mark.xfail(reason="BUG-004: table field accepts letters")
def test_table_number_only_accepts_digits():
    # This should fail — documenting a real bug
    ...

In my SV Burger project, I used it to document 3 real bugs I found. It felt like writing a bug report inside the code itself — which is exactly what it is.

📖 Concept

What is the Page Object Model, and why does it matter?

Imagine you have 10 tests that all click the same login button. Then the dev changes the button's ID. Now you have to update 10 tests. That's a maintenance nightmare.

With the Page Object Model (POM), you define the button once in a page class, and all tests use that class. One change, one fix.

class LoginPage:
    def __init__(self, driver):
        self.driver = driver
        self.btn = driver.find_element(By.ID, "login-btn")

    def click_login(self):
        self.btn.click()

POM isn't just a pattern — it's a way of thinking about maintainability. Your tests should break because the behavior changed, not because someone renamed a CSS class.

🐛 Bug Found

The field that accepted anything — and why that's a problem

While testing SV Burger, I found that the table number field accepted letters. You could type "abc" and the app wouldn't complain.

It sounds minor. But think about it: if that value gets stored in a database expecting an integer, you get a crash downstream — far from where the actual mistake happened. That's why input validation matters at the UI level, not just the backend.

Finding this reminded me that negative testing isn't about breaking things for fun. It's about asking: what happens when a real user makes a mistake?

BUG-004 | Severity: Medium
Field: Table Number
Expected: Only numeric input accepted
Actual: Accepts alphabetical characters
Status: Documented with @pytest.mark.xfail
💡 TIL

CI/CD made me realize testing is a team responsibility

Setting up GitHub Actions to run my tests automatically on every push was a turning point for me.

Before that, tests felt like something you run manually at the end. After that, they became part of the workflow — every change is validated, every regression is caught early.

name: Run Automated Tests
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: pytest test/

It also made me think about how QA fits in a team: it's not a final checkpoint. It's a continuous safety net. And automation is what makes that net scalable.

📖 Concept

Boundary testing: the edges are where bugs hide

Most bugs don't live in the middle. They live at the edges.

If a field accepts between 1 and 3 items, test with 0, 1, 3, and 4 — not just 2. The happy path is rarely where things break.

Test cases for "select meals (max 3)":
✅ Select 1 meal → should pass
✅ Select 3 meals → should pass (limit)
❌ Select 0 meals → should show error
❌ Select 4 meals → should be blocked

In my project, I found that the app allowed selecting more than 3 meal types when it shouldn't. The happy path worked fine. The boundary didn't. That's exactly why we test the edges.
